# Issue #3 日本語作業ログの品質改善（2026-07-14）

方針: 推測で作り込まず、実出力（5分スモーク＋2時間E2E、いずれも実会議）で確認できた弱点だけを直す。

## 品質ルーブリック（MS4UI arXiv:2506.12623 のtext summary観点を作業ログ向けに翻案）

| 基準 | 定義 | 現行評価（修正前→後） |
|---|---|---|
| 事実性 | 画面・発話にない情報を作らない | ○（プロンプトで抑制済み、#17浄化あり）ただし action="null" 素通りバグあり → **修正で◎** |
| 要約性 | 「何をしていたか」が短時間で掴めるか | △ 発話が生断片の列挙（相槌×3等）→ **連続重複圧縮で○**。1文要旨があれば◎（下記Q4） |
| 時系列一貫性 | 窓の意味論が一貫し滞在時間が合う | ◎（#18で窓解釈統一、2時間E2Eでアプリ別合計≒総時間を確認） |
| 可読性 | Markdownとして自然に読めるか | △「null」表示・重複行 → **○** |
| 検索性 | 後から検索・集計に使えるか | ◎（JSONL一次情報保持＋#5のsal-search） |

## 実施した修正（TDD、コミット2件）

1. **action空値正規化バグ修正**（`vlm_common.parse_fields`）: VLMが `"action": "null"` を返すと
   文字列"null"がそのままMarkdownに出ていた。`normalize_json_value` をactionにも適用し
   FALLBACK_ACTIONへ（実例: 2時間E2Eの先頭エントリで発生）
2. **連続重複発話の圧縮**（`domain/speech_filter.collapse_repeated_lines` 新設→`_attach_speech`配線）:
   「アドメット」×2「はい」×3のような連続同一行を1行に。間に別発話を挟む反復は会話の
   流れとして保持（全体dedupはしない）

## Q4: VLM＋小型テキストLLM分業の価値検証（実測）

2時間E2Eの発話リッチな10エントリ（35〜60行/エントリ）に対し、Qwen3-VL-4B-4bit（テキスト入力）で
「日本語1文要旨」を生成:

- 品質: 10/10で意味のある要約（例:「担当者PC不具合で待機、その後詳細情報共有の意図あり」）。
  誤認識断片からも文脈を正しく復元、固有名詞の捏造なし（プロンプトで抑制）
- 速度: **1.7〜2.8s/エントリ**（71エントリの2時間動画でも+2.4分、全体31分に対し8%増）
- 判断: **明確な価値あり → 実装は新Issueに切り出し**（発話要旨のオプトイン機能。
  8〜12GB機ではVLMとの同時常駐が厳しいためモデル使い回し設計が論点）

## Q5: 日本語特化VLM比較の処置（見送り・再訪条件つき）

- llm-jp-4-vl-9b-beta: MLX/GGUFポートなし → 本機で速度要件（実時間の2〜3割）を満たす実行経路がない
- Sarashina2.2-Vision-3B: GGUFのみ（llama.cpp系VLMは#8実測でvllm-mlx比40倍遅）
- **再訪条件: いずれかのMLXポート登場**（mlx-communityウォッチ）。現行Qwen3-VL-8Bの日本語出力は
  ルーブリック上の主要弱点ではないため、待つコストは低い
