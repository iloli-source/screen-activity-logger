実装前提と類似事例を確認したうえで、辛口で方式選定を出します。まずコードベースの現状と実践知を調べます。実装を踏まえた結論です。`--mode meeting` は現状 **OCRをキーフレーム限定するだけ**で、VLM間引きは未実装です。`PilFrameComparator` は OCRスキップ用の画素差、重複除去は `(action, resource)` 完全一致です。自リポの BEST_PRACTICES も既に「OCRテキスト差分をVLMトリガに」と書いており、本件はその実装遅延を突いています。

## 1. 推奨方式

**B を主ゲート ＋ A を安全弁（組み合わせ）。C は主手段にしない。**

判定の正本は次の2段に分ける。

| 段 | 役割 | 判定 |
|---|---|---|
| 候補生成 | 既存のまま | `fps` 抽出 ＋ `scene` → `is_keyframe` |
| VLM実行ゲート | **新規** | 候補キーフレームをOCRしたうえで、**最後にVLMを呼んだフレーム**のOCR集合と比較 |

```
should_vlm =
  first_keyframe
  OR ocr_jaccard(last_vlm_ocr, cur_ocr) < τ_skip
  OR elapsed_since_last_vlm >= max_gap
  OR (optional) forced by --min-keyframe-interval の下限は「最短再呼出し」ではなく debounce
```

**理由（実装者視点）**

1. **コスト構造が合う**  
   VLM 30–90秒/回が支配項。PaddleOCRは既に「支払い済み」か、キーフレーム限定でも VLM より桁違いに安い。フィルタは安い側に置くのが二段推論の定石（候補生成＝scene、最終ゲート＝内容）。

2. **失敗モードと信号が一致する**  
   話者ビュー切替は画素は激変するが、**読める文字（UI・チャット・共有資料）はほぼ不変** → Jaccard高 → スキップ。  
   画面共有開始・スライド切替・IDE操作は **新出文字が増える** → Jaccard低下 → 発火。  
   あなたが自覚しているハイブリッド（Circleback系）は、まさに B が救うケース。

3. **A 単独は自己矛盾**  
   テストデータに画面共有があるのに、`--mode meeting` + 60秒間引きを主戦略にすると、**自前の重要ケースを設計で捨てる**。モード分類をユーザーに押し付けるのも脆い（会議なのに共有デモ、作業なのに顔出し導入、など）。

4. **C は本件のノイズ源そのもの**  
   話者切替＝全画面顔入れ替え＝64×64 MAD が跳ねる。既存 `PilFrameComparator` を VLM ゲートに転用すると、**抑制したい現象で発火する**。OCRスキップ用途と VLM ゲート用途を混同しない。

5. **実践知との整合**  
   画面エージェント／ローカル作業ログ系（openrecall・screenpipe 系、自調査の「OCR密・VLM疎」）は、**生シーンスコアではなくコンテンツ（文字・UI）変化で高いモデルを叩く**。長尺動画理解でも keyframe は候補、最終選別は別シグナル、が一般的。  
   画素だけに頼る scene=0.08 は「編集点検出」向きで、「会議UIの意味変化検出」向きではない。

**`--mode` の位置づけ（重要）**

- `screencast` / `meeting` は **OCR密度ポリシー**（現状どおり）には残してよい。  
- VLM 間引きは **モード非依存の B+A** に寄せる。  
- `meeting` で「60秒固定」をデフォルトにするのは **hotfix 用の逃げ道** に留め、本線にしない。

## 2. 推奨方式の落とし穴・エッジケース（実装で必ず潰す）

### (1) 空OCR / 低情報量OCRで Jaccard が壊れる
話のみ・背景ぼかし・共有なし会議では両フレーム `lines=()` になりがち。  
空同士の Jaccard を 1.0 にすると **初回以降ずっと VLM スキップ**、0.0 にすると **毎回発火**。どちらも地雷。

**必須ポリシー**

- `|union| < N_min`（例: 正規化後トークン/行が 3 未満）→ Jaccard を信頼せず  
  - `max_gap` 経過なら強制 VLM  
  - 未経過ならスキップ（または弱い debounce）
- 片方だけ空 → **変化あり**（共有開始/終了）として VLM

### (2) 比較対象は「直前キーフレーム」ではなく「最後に VLM したフレーム」
連続キーフレーム同士の類似では、中間でスキップしたあとにドリフトする。  
また OCR の行分割ゆれで「直前とは違うが、VLM時点とは同じ」が起きる。  
状態は `last_vlm_ocr_lines` / `last_vlm_ts` を保持すること。

### (3) Meet/Zoom 固有の「文字ノイズ」で誤発火
- 話者名ラベルの入れ替わり  
- 録画中バッジ、参加者数、「〇〇さんが参加しました」  
- 時計・経過時間・未読数  
- チャット1行だけ流れる  

**正規化なしの生行 Jaccard は会議で過発火する。**  
前処理例: 小文字化、空白圧縮、長さ1の断片落とし、数字のみ行の除外、既知UI定型の除外（最初は控えめに）。

### (4) OCR は同じ UI でも行分割が非決定的
PaddleOCR は同一画面でも行の切れ目が揺れる。  
**行集合の完全一致前提は弱い。**  
対策: 行を空白区切りトークン集合にする、または短い n-gram 集合。完全一致 Jaccard よりロバスト。

### (5) 文字が変わらない意味変化を取りこぼす
- ホワイトボードの図だけ更新  
- Figma / 図解 / 動画再生の視覚変化  
- スライドが画像主体でテキスト差分が小さい  
- コードのシンタックスハイライトだけ・カーソル移動のみ（作業ログとしてはスキップでよいことも多い）

→ **B は「作業ログ（文字中心）に最適化されたゲート」**であり、映像理解全般の万能ゲートではない。だから **`max_gap`（Aの上限）を安全弁に必ず付ける**。取りこぼしは「遅延してでも1回は拾う」。

### (6) パイプライン順序・既存フラグとの衝突（このリポ特有）
現状 `GenerateWorklog` は `is_keyframe` なら無条件 `describe`。  
`meeting` は OCR をキーフレームのみ。  
B を入れると:

- キーフレーム候補は増えたまま OCR する（VLMより安い）  
- **VLM だけ** `should_describe` で落とす  

`is_keyframe` を間引きで書き換えないこと。  
キーフレーム＝scene候補、describe＝内容ゲート、と責務分離しないと、OCRポリシー・テスト・メトリクスが壊れる。

### (7) 事後 `(action, resource)` 畳みは VLM 節約に効かない
言い回しゆれ問題は **ゲート前削減** でしか解けない。  
B で呼べばエントリ自体が減るので、事後畳みの重要性は下がる。  
それでも残る重複には、埋め込み類似や構造化ラベル（後述）を別チケットにせよ。**今の完全一致 collapse に期待するな。**

### (8) 画面共有「中」の細かい操作
共有開始は拾える。共有中のクリック連打で OCR 差分が小さいと間引かれる。  
作業ログ用途なら多くは ASR＋OCR行で足りるが、手順再現が目的なら `screencast` か `τ` を厳しく（スキップしにくく）する。  
**1本の動画に会議パートとデモパートが混在するなら、時間モード固定より B の方がまだマシ。**

## 3. 却下・格下げした方式

| 方式 | 判定 | 理由 |
|---|---|---|
| **A 単独（60秒）** | 却下（主戦略として） | ハイブリッド取りこぼしが設計要件と衝突。モード誤指定で screencast も壊せる。実装は最短だが、**正しさの軸が「時間」で、問題の軸は「内容」**。 |
| **C 単独（画素類似）** | 却下 | 話者切替で差分最大＝本件の偽陽性そのもの。既存 comparator は OCR スキップ用（閾値0.02）で、VLM ゲートに流用すると逆効果。 |
| **C を顔マスク後に使う** | v1 却下、研究枠 | Meet/Zoom/Teams のレイアウト差、PiP、ギャラリー、共有時サイドパネルで顔領域定義が脆い。メンテコスト＞利得。 |
| **安いVLM/CLIPで事前判定（D）** | v1 見送り | M4 24GB で 8B VLM と同居するとメモリ競合。2モデル運用は運用地獄。まず決定的な OCR ゲートで十分。効かなくなってから embedding 二次ゲート。 |
| **レイアウト検出（タイル数・共有領域）** | v1 見送り | 製品UI依存で脆い。共有開始検出だけなら OCR 新出文字の方が汎用。 |
| **scene 閾値を上げるだけ** | 却下 | 会議ノイズとデモの操作変化を同じスカラーで分離できない。閾値上げは screencast を殺す。 |

**A を完全廃棄しない理由:**  
`max_gap`（強制サンプル）と、OCR 不安定時の debounce として **従属パラメータ** なら有用。主スイッチにしない。

## 4. パラメータ推奨値

実データ（Meet 5分で scene 6–26 回）でカリブレーション前提。初期値:

| パラメータ | 推奨初期値 | 意味 |
|---|---|---|
| `ocr_jaccard_skip` τ | **0.82** | これ以上似ていれば VLM スキップ。高いほど慎重（VLM多め）。0.75 は会議ノイズに甘い、0.90 は過発火寄り |
| OCR 正規化 | 必須 | strip / 空白圧縮 / 短行除去 / 数字のみ行除外 |
| 類似度の単位 | **トークン集合**（行集合より優先） | 行分割ゆれ耐性 |
| `N_min`（信頼最小 \|union\|） | **3** | 未満は Jaccard 無効 → `max_gap` 依存 |
| `max_gap`（強制 VLM） | **120s**（会議寄り） / 180s まで可 | 長尺の「同じ画面で話が続く」を完全無記録にしない安全弁 |
| `min_gap`（最短再呼出し） | **5–10s** | 同一秒付近の連続 scene を OCR コストも含め間引く debounce。**60s は大きすぎ** |
| 初回キーフレーム | 常に VLM | 固定 |
| scene 閾値 | **現状 0.08 のまま** | 候補生成は緩め、最終は B で落とす |
| `--mode meeting` | OCR=キーフレームのみ（現状） | VLM 間引きは mode 非依存の B+A |
| `--min-keyframe-interval` | **上書きは min_gap / max_gap の明示用** | 「meeting=60」のマジックナンバーを CLI に焼き込まない |

**チューニング手順（実装後すぐ）**

1. 会議のみ・共有なし 5本: VLM 回数が scene 回数の **1/5〜1/15** になるか  
2. 共有開始の ±2s に必ず VLM が立つか  
3. 共有中の手順デモで、主要画面遷移（ウィンドウ/URL/ダイアログ文字列変化）が落ちていないか  
4. screencast で τ=0.82 が操作ステップを潰していないか（潰すなら screencast は τ を上げる or B を弱める）

**期待効果の粗い見積もり**  
5分で scene 6–26 → 内容変化が 2–5 回なら、VLM はおおよそその回数＋`max_gap` 補完。7–41分が支配項なら、**会議動画は数倍〜一桁速くなる**想定。OCR 全キーフレーム化の追加コストは通常ノイズ。

## 実装メモ（このコードベース向け、辛口）

1. **`describe` の前にゲートを入れろ。** `TimelineMerger._collapse_consecutive` をいじっても処理時間は一秒も縮まない。  
2. **`is_keyframe` と `should_describe` を混ぜるな。** テストも `test_batch_and_meeting_mode` の OCR ポリシーと分離して書け。  
3. **A の 60秒案は「動くデモ」にはよいが「正しい設計」ではない。** Circleback に共有が含まれる時点で、A 主戦略は回帰テストで自分を撃つ。  
4. 余力があれば VLM 出力を短く構造化（`action` を動詞句固定、温度低）して事後畳みを救済するが、**それは品質問題で、今回のレイテンシ問題の本丸ではない。**

---

**一行まとめ:**  
VLM を減らす軸は時間でも画素でもなく **「前回 VLM 時から画面上の文字が意味的に変わったか」**。主ゲートは OCR Jaccard（B）、時間は `max_gap`/`min_gap` の安全弁（A）、画素類似（C）は本件では逆指標。
