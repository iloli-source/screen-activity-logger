# Issue #29 パイプライン並行化の実測記録（2026-07-17）

環境: M4 Air 24GB。実測データ: 実セミナー音声6.7h/1h・2時間実会議合成入力。

## 実装
1. **チャンク分割ASR**（既定30分・両側オーバーラップ30秒・帰属規則 chunk_start<=start<chunk_end）
2. **ステージ並行**: ASR（GPU/音声のみ）∥ 抽出+OCR（CPU）→ 合流後にVLM（ASR×VLMのGPU競合は構造上排除）
3. faster-whisperはCTranslate2 num_workersでチャンク並列（モデル共有・メモリ1本分）

## 実測結果

| 測定 | 結果 |
|---|---|
| cpp固定費（起動+ロード） | 1.7秒/チャンク → チャンク長の速度影響は無視できる |
| cppチャンク長 10/30/60分（実1h音声） | 486s/560s/356s＝**差はrun間ノイズ範囲、速度で選ぶ必要なし** |
| faster並列 workers1→3（実1h音声） | 1829s→1527s＝**1.2倍**（CT2が単独でも内部マルチスレッドのためM4 10コアでは伸び代小。出力は完全同一） |
| ステージ並行のE2E（2h入力） | 31.2分（旧30.8分と同等）＝**Macでは実質ニュートラル**（ASRチャンクのffmpeg抽出と フレーム抽出がCPUを取り合うため。ASRが支配的なCPU環境=Windowsで効く構造） |

## チャンク長の判断基準（ユーザー要望への回答）
- **速度では選ばない**（固定費1.7s×Nは総時間の1%未満、実測でも10/30/60分は同等）
- **下限**: 境界数を増やしすぎない・固定費比1%未満 → 10分以上
- **上限**: 失敗時の再開単位・並列時のロードバランス（総時間÷チャンク長 ≧ ワーカー数×2目安） → 60分以下
- **既定30分**: 6.7hで13境界・再開単位として実用的、の中庸

## 境界品質の修正（重要な発見）
lead-inのみの初期実装は**境界をまたぐ発話が前チャンクで尻切れ・次チャンクで破棄**され、
2h実測で境界毎に80〜160字欠落（合計90.1%）。両側オーバーラップ＋上下限帰属規則に修正し、
10秒で97.1%→**30秒で103.1%**（非分割比。文脈供給で微増）に回復。境界lapも旧水準以上。

## 結論
- チャンク分割: 品質同等以上・頑健性向上（チャンク単位の失敗隔離・有界メモリ）で**既定ON（30分）**
- 並列度: faster=自動（最大4、実測1.2倍）、GPU系=1固定
- ステージ並行: Macニュートラル・CPU環境で有効な構造として採用（回帰なし）
- 速度の次のボトルネックはOCR（#30）とVLM 2.2h（セミナー実測）
